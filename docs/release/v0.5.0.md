# wal-db v0.5.0 — Feature complete

**The feature set is done and frozen.** v0.5.0 adds the last two things a storage
engine needs from a WAL — replaying from a checkpoint (`iter_from`) and
truncating for compaction (`truncate_after`) — and records a baseline benchmark
suite. From here the remaining milestones are optimization and hardening, not new
surface.

## What is wal-db?

A write-ahead log primitive for Rust storage engines — the durability substrate
under `lsm-db`, `txn-db`, `raft-io`, and Hive DB. The append path is lock-free,
concurrent commits coalesce into one fsync, durability is platform-correct, the
log can be striped across bounded segment files, recovery is fuzz-hardened and
provable from a torn write, and records can be raw bytes or typed values.

## What's new in 0.5.0

### LSN seeking — `Wal::iter_from`

An LSN is a byte offset, so replaying from a checkpoint is O(1): iteration starts
at the LSN instead of scanning from the beginning.

```rust
use wal_db::{MemStore, Wal};

# fn main() -> Result<(), wal_db::WalError> {
let wal = Wal::with_store(MemStore::new())?;
wal.append(b"one")?;
let second = wal.append(b"two")?;
wal.append(b"three")?;

let from_second: Vec<Vec<u8>> = wal
    .iter_from(second)?
    .map(|entry| entry.map(|r| r.into_data()))
    .collect::<Result<_, _>>()?;
assert_eq!(from_second, vec![b"two".to_vec(), b"three".to_vec()]);
# Ok(())
# }
```

### Compaction truncation — `Wal::truncate_after`

When a consumer has durably applied the log up to a point, it can drop everything
after that record. `truncate_after` keeps the log up to and including the given
LSN, makes the truncation durable, and lets appends resume from the clean end —
across both single-file and segmented logs.

```rust
use wal_db::{MemStore, Wal};

# fn main() -> Result<(), wal_db::WalError> {
let wal = Wal::with_store(MemStore::new())?;
wal.append(b"keep me")?;
let last_kept = wal.append(b"and me")?;
wal.append(b"drop me")?;

wal.truncate_after(last_kept)?;
assert_eq!(wal.iter()?.count(), 2);
# Ok(())
# }
```

It requires exclusive access — no concurrent appends or syncs — which is the
natural shape of compaction: the engine pauses the log, truncates, and resumes.

### Recorded benchmarks

[`docs/BENCHMARKS.md`](../BENCHMARKS.md) records baseline numbers for the append,
single-commit, group-commit, and recovery paths, with method and how to reproduce.
A new `recovery/replay` benchmark measures reopening a 10k-record log and replaying
it. The headline figures, on the development machine with 256-byte records:

- `append/single` ≈ 120 ns (lock-free, no I/O)
- `append/multi` (8 writers) ≈ 4.1 M appends/s
- group commit ≈ 4.6× the single-writer commit rate
- `recovery/replay` ≈ 209 K records/s

The commit figures are fsync-bound on this machine; an honest cross-engine
comparison is the subject of the 0.6 optimization milestone.

### On async

No async wrapper is shipped. The core is synchronous on purpose — a WAL's calls
map to blocking syscalls, and the runtime is the consumer's choice — so the crate
stays runtime-agnostic. From an async context, offload to a blocking pool:

```rust,ignore
let wal = wal.clone(); // Arc<Wal>
let lsn = tokio::task::spawn_blocking(move || wal.append_and_sync(b"record")).await??;
```

## Breaking changes

**None.** `iter_from` and `truncate_after` are new methods. A log written by any
earlier 0.x release is read by 0.5.0 unchanged.

## Fixes folded in

Two issues found after 0.4.0 (which was never published) are fixed here:

- `cargo doc` on the default feature set failed because the always-present
  `WalError::Encoding` doc linked the `pack-io`-only typed methods; the links are
  now plain code spans, and CI runs `doc`/`clippy`/`test` on both default and
  `--all-features`.
- The CI fuzz job built for musl (where ASAN can't link static libc) because the
  prebuilt `cargo-fuzz` is musl-static; the fuzz build is now pinned to gnu.
