# wal-db v1.1.1 — Durability fixes

Three fixes to what `sync` and `truncate_before` promise. No API or on-disk format
change. One behaviour change: after a failed `sync`, later syncs keep failing until
the log is reopened.

## What's fixed

### A torn `head` marker could cost a whole segmented log

`truncate_before` rewrote the `head` marker in place, so a crash could leave it
empty. The head then fell back to 0, below the segments already dropped, and a
default open cut the log to nothing and deleted every segment. The marker is now
written to `head.tmp`, flushed, renamed over `head`, and the directory is flushed,
so a crash leaves the old marker or the new one.

### New files were not durable until their directory was

On Unix, flushing a file does not make its name durable, so a power loss could lose
a segment whose records had already been synced. `sync` now flushes the directory
after a segment file is created or removed, and once per open for both store types,
which covers a new single-file log and a new log directory. Removals matter too: a
truncated segment that came back after a power loss could bring truncated records
with it.

### A failed flush could be followed by a false `Ok`

After a failed flush the operating system may have dropped the pages it could not
write and marked them clean, so a retry can succeed without them reaching the disk.
A caller could hit this by retrying, and so could any thread waiting on the failed
flush, because waiters retried it themselves.

Now every waiting thread gets the error, and every later `sync` covering anything
not yet durable returns `WalError::Io` until the log is reopened. Records that were
already durable stay durable, and a sync for them still returns `Ok`.

## Upgrading from 1.1.0

No code changes are needed. If your code retries `sync` after an error, it will now
keep getting the error: stop appending and reopen the log, as the docs have always
advised.

## Cost

One directory flush per new or removed segment and per open, inside `sync`, never in
`append`. The append path pays one atomic store per new segment.

Windows has no directory flush through the standard library, so that step is a no-op
there; NTFS commits metadata through its journal. A directory that cannot be opened
for lack of permission, or a filesystem that does not support the flush, is skipped.

## Installation

```toml
[dependencies]
wal-db = "1.1"
```

MSRV: Rust 1.85.
