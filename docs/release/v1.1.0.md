# wal-db v1.1.0 — Strict open

**Fail closed on damage in the middle of the log.** Opening a log cuts everything
from the first damaged record on. That is right for a torn tail left by a crash
mid-append, but when the damage is in the middle of the log (bit rot, a bad
sector, a missing segment file) it also cuts the intact, acknowledged records
after it, and the caller cannot tell. v1.1.0 adds an opt-in `OpenPolicy::Strict`
that refuses to open in that case, and `Wal::truncated_on_open` to report what any
open cut. Additive: the default behaviour, the 1.0 API, and the on-disk format are
unchanged.

## What's new in 1.1.0

### `OpenPolicy` — what opening does with damage

```rust
use wal_db::{OpenPolicy, Wal, WalConfig, WalError};

# fn main() -> Result<(), WalError> {
# let dir = tempfile::tempdir().map_err(WalError::from)?;
# let path = dir.path().join("app.wal");
let config = WalConfig::new().with_open_policy(OpenPolicy::Strict);
match Wal::open_with(&path, config) {
    Ok(wal) => println!("opened; cut {} torn bytes", wal.truncated_on_open()),
    Err(WalError::Corruption { offset, reason }) => {
        eprintln!("refusing to open: {reason} at {offset}"); // nothing was cut
    }
    Err(other) => return Err(other),
}
# Ok(())
# }
```

- `OpenPolicy::TruncateTail` (default): cut from the first damaged record to the
  end. Exactly the 1.0 behaviour.
- `OpenPolicy::Strict`: cut a damaged or incomplete final record, but if an intact
  record follows the damage, or the store cannot read back bytes it reports
  holding (missing segment files, or segments below a lost head marker), return
  `WalError::Corruption` at the damaged record's offset and leave the store
  untouched. An intact record longer than the configured `max_record_size` (a
  log written with a larger limit) is refused the same way, not cut.

Strict open tries every byte offset after the damage as a record start, because
damage to a length field leaves the next record's position unknown. Candidates
longer than the 64 KiB read window are checked from prefix checksums, so the cost
of one candidate does not grow with its length. There is no cost on a log that
opens clean.

**When it refuses a log that was only torn.** The check cannot tell damage from a
crash that left a later record complete behind an incomplete earlier one, which
happens when several appends are in flight together. It is exact for a log
written one record at a time, each made durable before the next is appended
(`append_and_sync`, or `append` then `sync`). Every refusal fails closed;
reopening with the default policy after inspection cuts as before.

### `Wal::truncated_on_open`

How many bytes the open scan cut, under either policy. Zero when the log opened
clean. Under `Strict` a non-zero value is only ever a torn tail; under the
default it can include intact records that followed mid-log damage.

## Cost

Measured with `cargo bench --bench wal_bench -- recovery/strict_torn_tail`, a
torn tail of random bytes (the worst case), in memory:

| Torn tail | Default open | Strict open |
|-----------|--------------|-------------|
| 64 KiB    | ~0.15 ms | ~0.33 ms |
| 1 MiB     | ~0.72 ms | ~4.9 ms  |
| 16 MiB    | ~11 ms   | ~187 ms  |

Details in [`docs/BENCHMARKS.md`](../BENCHMARKS.md).

## Testing

- `tests/strict_open.rs`: torn tails cut under both policies; damage to the
  payload, length, and checksum fields in the middle of the log refused under
  `Strict` with the file byte-for-byte unchanged; the default still cutting;
  segmented logs, including missing middle segments and a lost head marker
  after prefix compaction; a record above a lowered `max_record_size`; property
  tests over random truncation points (both policies agree) and random
  single-byte damage before the last record (strict refuses at that record,
  default keeps what precedes it).
- Unit tests for the scan itself, including the prefix-checksum arithmetic
  checked against direct checksums.
- The fuzz target now also opens every input under `Strict`.

## Upgrading from 1.0.x

Nothing to do. Existing code compiles and behaves as before. To fail closed on
mid-log damage, add `.with_open_policy(OpenPolicy::Strict)` to the `WalConfig`
passed to `open_with`, `open_segmented_with`, or `with_store_and_config`.
