# wal-db v0.9.1 — Release-candidate hardening

**Closing the last integrity gap before 1.0.** Reviewing 0.9.0 as a 1.0 candidate
surfaced one flaw worth a patch: the prefix-compaction `head` marker was not
crash-safe against a torn write of *itself*. 0.9.1 makes it self-validating, soaks
the feature with a property test, and corrects a doc inaccuracy. No API change.

## What is wal-db?

A write-ahead log primitive for Rust storage engines — the durability substrate
under `lsm-db`, `txn-db`, `raft-io`, and Hive DB. Lock-free append, group commit,
platform-correct durability, segment rotation, fuzz-hardened recovery, recovery
policies, LSN seeking, suffix and prefix compaction, and optional typed records.

## What's new in 0.9.1

### A checksummed `head` marker

When a segmented log drops a prefix, it records the new head — the first surviving
record's offset — in a small `head` file, flushed before any segment is deleted.
In 0.9.0 that file was 8 bare bytes. If a crash tore *that* write, a later open
would read whatever bytes were there and trust them; a plausible-but-wrong head
could make recovery skip live records. For a durability primitive, a silent
data-skip path is exactly what a frozen 1.0 must not carry.

The marker is now `[head: u64][crc32c: u32]`. On open, a marker that is missing,
short, or whose checksum does not match is ignored, and the head falls back to 0
so recovery reads the **whole** log. That fallback is always safe: a dropped
prefix the marker can no longer vouch for is simply read again — never lost. A
torn marker can no longer cause silent under-recovery.

### Soaked with a property test

A new property test runs `truncate_before` across random record sets, segment
sizes, and truncation points, asserting after each reopen that every record from
the checkpoint onward reads back with its original bytes and LSN — exercising the
spanning case (where the lowest surviving segment begins mid-record) over hundreds
of generated inputs. A companion test proves a torn marker falls back to full
recovery with no data loss.

### Documentation correction

`truncate_before` returns the **exact** checkpoint LSN — reading resumes precisely
there — while *reclamation* is segment-granular (whole leading segment files). The
0.9.0 docs described the head as possibly sitting "at the start of the segment,"
which was inaccurate; the API reference, the rustdoc, and the on-disk format spec
are corrected.

## Breaking changes

**None.** No API change. The on-disk `head` marker grew from 8 to 12 bytes, but it
is brand new in 0.9.0 and is not part of the frozen record/segment format; an
older 8-byte marker is ignored on open and the log recovers in full.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS via the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTFLAGS="--cfg loom" cargo test --test loom_wal
cargo +nightly fuzz run recover --target x86_64-unknown-linux-gnu -- -max_total_time=60
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 build --all-features
cargo audit
cargo deny check
```

All green on both platforms; 119 tests pass, the property test soaks prefix
compaction over hundreds of cases, the fuzzer ran millions of inputs with no
crash, and loom passed.

## What's next

- **1.0.0.** With this gap closed, the library is a 1.0 candidate: feature
  complete, API and on-disk format frozen, and hardened by fuzz, loom, adversarial,
  fault-injection, and property tests. A stability soak (ideally one real consumer)
  is the remaining step before cutting the stable release.
