# wal-db v0.8.0 — Accuracy, examples, and audit

**The polish before consumer integration.** v0.8.0 makes the documentation
accurate to the code down to the version strings, widens the example and edge-case
coverage, and records an audit of the hot path and the integrity guarantees. No
public API change.

## What is wal-db?

A write-ahead log primitive for Rust storage engines — the durability substrate
under `lsm-db`, `txn-db`, `raft-io`, and Hive DB. Lock-free append, group commit,
platform-correct durability, segment rotation, fuzz-hardened recovery, recovery
policies, LSN seeking and truncation, and optional typed records.

## What's new in 0.8.0

### Documentation, accurate to the code

Every version string and status line now reflects the current release. The
`docs/API.md` reference — which still carried a "0.2 foundation" status header and
stale install snippets — is corrected, and its tier tables now list the segment
and recovery-policy surface that shipped after the tables were first written. The
API reference documents every public item, each with a description, its
parameters, its errors, and runnable examples for its use cases.

### Wider examples and edge coverage

- A new `checkpoint` example shows the seek-and-truncate workflow end to end:
  replay from a checkpoint LSN with `iter_from`, then truncate the log back to it
  with `truncate_after`.
- `tests/edge.rs` pins the boundaries: a record exactly at the size limit is
  accepted and one byte over is rejected; a maximum-size record round-trips
  through recovery; a thousand empty records and a hundred alternating
  empty/full records keep their order; the on-disk image is **byte-for-byte
  deterministic** (what makes a log portable across machines); and `len` /
  `is_empty` track the log exactly.

The crate now has five runnable examples (`basic`, `recovery`, `concurrent`,
`checkpoint`, `typed`) and 113 tests, plus the fuzz target and loom model checks.

### Audit

A review of the codebase against peak performance, energy, concurrency, security,
and data-integrity confirmed it is at the level the design allows, with nothing
warranting a change:

- **Performance / energy.** The LSN reservation is a single ~4 ns atomic; framing
  is allocation-free (a reused thread-local buffer) with a hardware CRC32C; the
  recovery scan reuses one buffer. A file append is syscall-bound — the `pwrite`
  the page-cache contract requires — not lock-bound, so there is no idle spinning
  and no superfluous syscall.
- **Concurrency.** The append data plane is lock-free; the durable watermark is
  computed under a short, loom-verified lock and is *conservative* — it never
  reports a byte durable that is not. Group commit coalesces fsyncs.
- **Security / integrity.** Every on-disk length is validated against the maximum
  before any allocation (fuzz-verified, millions of inputs, no panic or
  over-allocation); offset arithmetic on the recovery paths is checked; a failed
  write fail-stops the log; each record is checksummed with CRC32C, the industry
  storage standard.

**None.** This release changes documentation, examples, and tests; it touches no

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS via the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTFLAGS="--cfg loom" cargo test --test loom_wal
cargo +nightly fuzz run recover --target x86_64-unknown-linux-gnu -- -max_total_time=60
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 build --all-features
cargo audit
cargo deny check
```

All green on both platforms; 113 tests pass, every example runs, the fuzzer ran
millions of inputs with no crash, and loom passed.
