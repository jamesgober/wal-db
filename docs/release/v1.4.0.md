# wal-db v1.4.0 - Durable segments

Durability and data-safety fixes. The record
format is unchanged and every existing log opens. Segmented logs gain a `meta`
file recording their segment size, which older readers ignore.

## The critical fix

`SegmentedStore::sync` chose the segments to flush from the highest byte
written. Bytes written late into an older segment, or left unflushed by a
process that stopped, were acknowledged while still dirty in the page cache,
so a power loss could take records `sync` had promised. Every segment now
carries a dirty flag, a sync flushes every dirty segment, and an open flushes
every existing segment before recovery trusts it. `tests/page_cache.rs`
checks the page cache's dirty count with `cachestat(2)` on Linux (run in CI).

## Opens that no longer delete data

Each of these used to cut or delete synced records under the default policy;
now it is refused with `Corruption` and the files are kept:

- a lost or damaged `head` marker after a prefix drop;
- a segmented log opened with another segment size (now recorded in `meta`);
- a file whose first record does not verify (not a log);
- an intact record above a lowered `max_record_size`;
- `truncate_before` at an offset that is not a record.

## Also fixed

- `truncate_after` at a segment boundary removes the next segment and flushes
  the shrink.
- A panic inside `append` no longer wedges every later `sync`.
- A failed sync inside `truncate_after` is permanent for the handle.
- Recovery no longer allocates a length the store cannot back.

## Typed records

The example, README, and crate docs now use `pack-io-2` (`append_pack`,
`Record::unpack`); `Record::decode` (pack-io 1.0) documents its exposure to
hostile input.

## Upgrading

`wal-db = "1.4"`. A program that opened a non-log file, or relied on the
default policy cutting the cases above, now gets `Corruption` instead. The MSRV
stays 1.85.
