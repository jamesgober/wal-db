# wal-db v0.6.0 — Optimization

**Measured, not guessed.** v0.6.0 is the performance pass: a full benchmark suite,
a head-to-head against a hand-rolled WAL, and the optimizations the measurements
actually justified — no more, no less. The headline result is that wal-db's group
commit beats the inline WAL an engine writes before it has batching by ~1.9×, and
the headline *discipline* is what was deliberately **not** changed.

## What is wal-db?

A write-ahead log primitive for Rust storage engines — the durability substrate
under `lsm-db`, `txn-db`, `raft-io`, and Hive DB. The append path is lock-free,
concurrent commits coalesce into one fsync, durability is platform-correct, the
log can be striped across bounded segment files, recovery is fuzz-hardened, and
records can be raw bytes or typed values.

## What's new in 0.6.0

### A benchmark suite, and what it found

The criterion suite now covers the LSN reservation, single- and multi-writer
append, single and group commit, and recovery. Measured on the development
machine with 256-byte records:

| Benchmark | Result |
|-----------|--------|
| LSN reservation (`fetch_add`) | ~4 ns |
| `append/single` (memstore) | ~105 ns |
| `append/multi` (8, filestore) | ~160 K/s (syscall-bound) |
| `commit/group` (8, filestore) | ~3.5 K commits/s |
| `recovery/replay` (10k) | ~215 K records/s |

Two findings shaped the milestone:

1. **The reservation is ~4 ns** — a single `AtomicU64::fetch_add`. Allocating an
   LSN and a byte range is as cheap as it can be.
2. **A file-backed append is syscall-bound, not lock-bound.** The ~6 µs/append
   under eight writers is the `pwrite` the page-cache durability contract
   requires; the commit-watermark mutex (tens of ns) is negligible against it.

### The optimization that mattered, and the one that didn't

- **Recovery scan, allocation-free.** The scan reused nothing — it allocated a
  buffer per record just to checksum it. It now reuses one buffer, cutting
  recovery-replay time ~12%.
- **The lock-free watermark rewrite was deliberately not done.** It was the
  obvious "optimization" on paper — remove the per-append mutex. But the
  measurement is unambiguous: the append is syscall-bound, so removing the mutex
  would not move the number, while a lock-free contiguous-write watermark is
  exactly the kind of subtle concurrent code that loses data when it is wrong.
  Trading a real integrity guarantee for an immeasurable gain is a bad deal. The
  append data plane stays lock-free; the watermark keeps its short, correct,
  loom-verified lock.
- **O_DIRECT was evaluated and skipped.** It needs every buffer, offset, and size
  aligned to 512/4096 bytes — which a variable-size record stream violates — and
  it reduces neither the per-append syscall nor the fsync. No clear benefit here,
  a lot of complexity; not implemented.

### Head-to-head — `cargo bench --bench compare`

Eight threads each commit durably to a file, identical workload:

| Contender | Throughput | Relative |
|-----------|------------|----------|
| **wal-db / group commit** | ~3.5 K commits/s | **1.9×** |
| naive `Mutex<File>` + fsync-per-commit | ~1.9 K commits/s | 1.0× |

The naive WAL is what an engine hand-rolls before group commit: a global lock and
an fsync on every commit. wal-db coalesces the fsyncs and never takes a global
lock on the write path, so it is ~1.9× faster here — and the gap widens with more
writers and faster storage. The figures are fsync-bound on this machine, so the
**ratio** is the signal. Full numbers and method: [`docs/BENCHMARKS.md`](../BENCHMARKS.md).

Full embedded databases (sled, redb) are not in the comparison: they are not WALs,
and benchmarking a durability primitive against a complete B-tree / LSM engine
would mislead. The WAL's job is to be the fast substrate *under* such systems.

## Breaking changes

**None.** This release changes no public API — only internals, benchmarks, and
docs.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS via the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTFLAGS="--cfg loom" cargo test --test loom_wal
cargo +nightly fuzz run recover --target x86_64-unknown-linux-gnu -- -max_total_time=60
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 build --all-features
cargo audit
cargo deny check
cargo bench --bench wal_bench
cargo bench --bench compare
```

All green on both platforms; the fuzzer re-validated the recovery change over
millions of inputs with no crash, and no tracked baseline regressed.

## What's next

- **0.7.0 — Hardening + API freeze.** Hostile recovery inputs (corrupted segments,
  truncated files, garbage prefixes), disk-full and fsync-failure edge cases,
  cross-platform durability re-verified, and the API frozen.
