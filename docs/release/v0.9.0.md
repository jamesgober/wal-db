# wal-db v0.9.0 — Prefix compaction

**Reclaiming old records.** v0.9.0 adds `truncate_before` — the complement to the
suffix `truncate_after` from 0.5 — so a consumer that has applied and flushed the
log up to a checkpoint can drop everything before it and get the disk back. On a
segmented log it deletes whole leading segment files; surviving records keep their
LSNs. Additive — no breaking changes.

## What is wal-db?

A write-ahead log primitive for Rust storage engines — the durability substrate
under `lsm-db`, `txn-db`, `raft-io`, and Hive DB. Lock-free append, group commit,
platform-correct durability, segment rotation, fuzz-hardened recovery, recovery
policies, LSN seeking, and optional typed records.

## What's new in 0.9.0

### `Wal::truncate_before` — prefix compaction

`truncate_after(lsn)` drops everything after a record (rolling back a tail, the
way a Raft log does on a conflict). `truncate_before(lsn)` is its mirror: it drops
everything *before* a record, the building block of checkpoint compaction.

```rust
use wal_db::Wal;

# fn main() -> Result<(), wal_db::WalError> {
# let dir = tempfile::tempdir().map_err(wal_db::WalError::from)?;
// Small segments so a handful of records spans several files.
let wal = Wal::open_segmented(dir.path(), 32)?;
for i in 0..10 {
    let _ = wal.append(format!("record {i}").as_bytes())?;
}
let checkpoint = wal.append(b"checkpoint")?;
wal.sync()?;

// Once the engine has durably applied through the checkpoint, reclaim the rest.
let head = wal.truncate_before(checkpoint)?;
assert!(head <= checkpoint);
// Surviving records keep their LSNs; iteration resumes from the head.
assert!(wal.iter()?.next().unwrap()?.lsn() >= head);
# Ok(())
# }
```

On a **segmented** log it deletes whole leading segment files and the segment with
the most recent records is never dropped, so the returned head may sit at the
start of the segment that still holds the checkpoint. A **single-file** log cannot
reclaim a prefix without moving the surviving bytes — which would change their
LSNs — so it is left unchanged and returns `Lsn(0)`. Like `truncate_after`, it
requires exclusive access (no concurrent writers or readers).

### Correct across crashes, with spanning records

Records span segment boundaries, so after dropping a prefix the lowest surviving
segment can begin in the middle of a record — and recovery cannot guess where the
first complete record starts. So the log records its **head** (the first surviving
record's offset, a real boundary) in a small `head` file, flushed *before* any
segment is deleted. A crash mid-compaction still recovers from the right boundary,
and recovery and iteration resume from the head rather than from 0. For
single-file and never-compacted logs the head stays 0 and nothing changes.

The on-disk addition is documented in [`docs/ON_DISK_FORMAT.md`](../ON_DISK_FORMAT.md):
an optional `head` file (8 little-endian bytes), absent until the first prefix
truncation.

## Breaking changes

**None.** `truncate_before`, and the `WalStore::head` / `truncate_before` trait
methods, are additive (the trait methods have defaults). A log written by any
earlier 0.x release is read by 0.9.0 unchanged.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS via the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTFLAGS="--cfg loom" cargo test --test loom_wal
cargo +nightly fuzz run recover --target x86_64-unknown-linux-gnu -- -max_total_time=60
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 build --all-features
cargo audit
cargo deny check
```

All green on both platforms; 118 tests pass — including a prefix-compaction
round-trip across a reopen (where the lowest segment starts mid-record) and a
corrupt-head-marker case that must not crash recovery — the fuzzer ran millions of
inputs with no crash, and loom passed.
